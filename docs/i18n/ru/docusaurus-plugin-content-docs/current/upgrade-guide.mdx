# Переход с 1.x на 2.x

<PageLead>
Выполните эти шаги при переходе существующего приложения с Laravel Feeds `1.x` на `2.x`. Если установленная версия `1.x` уже содержит slug фидов или обновлённые названия новых регистраций, сохраните эти изменения и пропустите выполненные шаги.
</PageLead>

## Требования к окружению {/* #runtime-requirements */}

| Компонент | `1.x` | `2.x` |
| --- | --- | --- |
| PHP | `^8.2` | `^8.4` |
| Компоненты Laravel | `^11.0 \|\| ^12.0 \|\| ^13.0` | `^13.0` |

Перед установкой `2.x` обновите зависимости Laravel приложения и версии PHP для веб-приложения, CLI, планировщика и обработчиков очереди. Приложения на PHP `8.2` или `8.3`, либо Laravel `11.x` или `12.x`, должны оставаться на `1.x`. Требования к окружению приведены на странице [совместимости](./compatibility.mdx).

## Перед обновлением {/* #before-upgrading */}

1. Сохраните текущий код приложения, `composer.json`, `composer.lock` и опубликованный `config/feeds.php`. Создайте резервную копию таблицы регистраций фидов и выходных файлов, необходимых для отката.
2. Запишите идентификаторы регистраций, названия, существующие slug, расписания и места выходных файлов.
3. Найдите вызовы `feed:generate` в скриптах развёртывания, заданиях cron, ручных расписаниях, тестах и коде приложения.
4. Сгенерируйте типовые фиды и сохраните их для сравнения.
5. При развёртывании приостановите расписания фидов и завершите выполняемые задания и задания в очереди до замены пакета и изменения схемы.

## Применение обновления {/* #apply-update */}

```bash
composer require dragon-code/laravel-feeds:^2.0 --with-all-dependencies
composer check-platform-reqs
```

Сравните `config/feeds.php` установленного пакета с опубликованной копией приложения и сохраните настройки приложения. Не публикуйте повторно с `--force`: это перезаписывает копию.

## Добавление slug фидов {/* #feed-slugs */}

[PR #287](https://github.com/TheDragonCode/laravel-feeds/pull/287) меняет выбор одного фида: вместо идентификатора базы данных используется slug, полученный через `Str::slug(title)`.

Если миграция slug пакета уже выполнена, не копируйте и не запускайте её повторно. Иначе:

1. Скопируйте только `vendor/dragon-code/laravel-feeds/database/migrations/2026_10_14_000000_add_slug_to_feeds_table.php` в каталог `database/migrations` приложения.
2. Задайте timestamp имени файла сразу после фактической миграции `create_feeds_table` приложения и перед всеми миграциями регистрации фидов. Сохраните суффикс `add_slug_to_feeds_table`. При таком порядке новая база данных тоже создаёт регистрации после добавления колонки slug.
3. Убедитесь, что `feeds.table.connection` и `feeds.table.table` указывают на существующую таблицу регистраций, затем выполните миграции:

```bash
php artisan migrate
```

Миграция добавляет nullable-колонку `slug` и заполняет её из существующих названий, включая мягко удалённые записи. Существующие названия и идентификаторы сохраняются. Не публикуйте повторно и не запускайте исходную миграцию создания таблицы.

:::warning
Если приложение уже использует собственную колонку `slug`, а миграция пакета ещё не выполнена, миграция завершится ошибкой до заполнения данных. Разрешите конфликт схемы до развёртывания; не удаляйте колонку приложения без сохранения её данных и обновления кода, который её использует.
:::

Посмотрите сохранённые значения в `php artisan tinker`:

```php
app(\DragonCode\LaravelFeed\Queries\FeedQuery::class)
    ->all()
    ->get(['id', 'title', 'slug']);
```

Slug для выбора фидов должны быть непустыми и различаться среди всех неудалённых регистраций, включая неактивные. Разные названия могут преобразоваться в одинаковый slug. Неоднозначный поиск вызывает `MultipleRecordsFoundException`; неизвестный slug — `FeedNotFoundException`. Исправьте коллизии или пустые slug, обновив названия через модель фида.

Сохранение модели фида пересчитывает slug из сохранённого названия. Массовые вставки и обновления через Query Builder обходят это поведение. Проверьте такие записи и пользовательские модели фидов, переопределяющие приведения типов или события модели.

## Замена ID в вызовах генерации {/* #generation-calls */}

Для регистрации с ID `42` и сохранённым названием `Products Feed` slug после миграции будет `products-feed`.

До:

```bash
php artisan feed:generate 42
```

После:

```bash
php artisan feed:generate products-feed
```

В `2.x` аргумент всегда означает slug; числовая строка больше не выбирает запись по ID базы данных. Вызов `php artisan feed:generate` без аргумента по-прежнему обрабатывает все активные регистрации. При использовании `--target` замените только аргумент регистрации; ключи целей остаются прежними:

```bash
php artisan feed:generate products-feed --target=42
```

Так же обновите ручные расписания и программные вызовы команды. До:

```php
use DragonCode\LaravelFeed\Commands\FeedGenerateCommand;
use Illuminate\Support\Facades\Schedule;

Schedule::command(FeedGenerateCommand::class, [42])->daily();
```

После:

```php
use DragonCode\LaravelFeed\Commands\FeedGenerateCommand;
use Illuminate\Support\Facades\Schedule;

Schedule::command(FeedGenerateCommand::class, ['products-feed'])->daily();
```

Сохраните настройки защиты от одновременного запуска, фонового выполнения и частоты ручного расписания. При переименовании регистраций обновляйте slug, указанные в коде. `ScheduleFeedHelper::register()` автоматически использует сохранённые slug и сохраняет привязку блокировок к регистрации при изменении её названия или выражения cron.

`FeedQuery::find(int $id)`, `delete(int $id)` и `restore(int $id)` по-прежнему используют ID. Для выбора по slug используйте `FeedQuery::findBySlug(string $slug)`. См. [генерацию и расписания](./generation.mdx).

## Проверка создаваемых названий {/* #generated-titles */}

[PR #293](https://github.com/TheDragonCode/laravel-feeds/pull/293) удаляет суффикс `Feed` из названий в новых миграциях регистрации или операциях развёртывания, создаваемых командой `make:feed`.

Для `php artisan make:feed ProductsFeed`:

| Значение | До | После |
| --- | --- | --- |
| Создаваемое название регистрации | `Products Feed` | `Products` |
| Slug из этого названия | `products-feed` | `products` |

Существующие названия в базе данных и ранее созданные файлы регистрации не перезаписываются. Используйте фактический сохранённый slug каждой регистрации. Это изменение названий не меняет имя класса фида и имя выходного файла.

## Документация и разработка пакета {/* #documentation-and-development */}

[PR #294](https://github.com/TheDragonCode/laravel-feeds/pull/294) переименовывает страницу документации Machine Learning в [ИИ-агенты](./ai-agents.mdx). Страница теперь доступна по адресу `/ai-agents/`; перенаправления сохраняют работу ссылок на прежний URL.

[PR #297](https://github.com/TheDragonCode/laravel-feeds/pull/297) задаёт новые требования к окружению и сохраняет документацию `1.x`. Выберите версию документации, которая соответствует установленному пакету; результаты поиска и контекст LLM ограничены этой версией.

Среда разработки самого пакета переходит на Pest `^5.0` и Testbench `^11.0`. Команды Pest пакета используют `--tia`, а для полного повторного запуска в CI, бенчмарках и обновлении снимков — `--fresh`. Это зависимости разработки пакета, а не требования к тестам приложения.

## Проверка {/* #verify */}

- Пересоберите кеш конфигурации приложения, если он используется, и перезапустите обработчики очереди и долгоживущие процессы планировщика с новым кодом.
- Убедитесь, что у каждой выбираемой регистрации непустой уникальный slug и что команды и ручные расписания используют его.
- Сгенерируйте фид каждого используемого формата; сравните количество разделённых файлов, имена и типовое содержимое с сохранённым результатом `1.x`.
- Проверьте выбор целей, автоматические и ручные расписания, а также генерацию через очередь, если они используются.
- Запустите тесты приложения для пользовательских моделей фидов, преобразователей, макросов и классов предустановок.
- Возобновите расписания фидов и обработку очереди после успешной проверки схемы и генерации.

## Откат {/* #rollback */}

Снова приостановите генерацию фидов и завершите выполняемые задания. Восстановите предыдущие код приложения, `composer.json`, `composer.lock`, конфигурацию и команды генерации, затем выполните `composer install` в совместимом окружении.

Применяйте политику отката миграций приложения только после проверки, использует ли восстанавливаемый пакет `1.x` slug. Метод `down()` миграции slug удаляет только эту колонку; он не восстанавливает переименованные записи или выходные файлы. При необходимости восстановите изменённые данные регистраций и выходные файлы из резервных копий. Перед возобновлением генерации пересоберите кеш конфигурации и перезапустите обработчики очереди и процессы планировщика.
