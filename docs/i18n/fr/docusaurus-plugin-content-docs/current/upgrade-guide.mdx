# Passer de la version 1.x à la version 2.x

<PageLead>
Suivez ces étapes pour passer une application existante de Laravel Feeds `1.x` à `2.x`. Si votre version installée de `1.x` inclut déjà les slugs des flux ou les nouveaux titres générés, conservez ces modifications et ignorez les étapes déjà effectuées.
</PageLead>

## Exigences d’exécution {/* #runtime-requirements */}

| Composant | `1.x` | `2.x` |
| --- | --- | --- |
| PHP | `^8.2` | `^8.4` |
| Composants Laravel | `^11.0 \|\| ^12.0 \|\| ^13.0` | `^13.0` |

Avant d’installer `2.x`, mettez à jour les dépendances Laravel de l’application et les environnements PHP utilisés par l’application web, la CLI, le planificateur et les workers de file d’attente. Les applications utilisant PHP `8.2` ou `8.3`, ou Laravel `11.x` ou `12.x`, doivent rester sur `1.x`. Consultez la [compatibilité](./compatibility.mdx) pour connaître l’environnement pris en charge.

## Avant la mise à niveau {/* #before-upgrading */}

1. Sauvegardez le code actuel de l’application, `composer.json`, `composer.lock` et le fichier `config/feeds.php` publié. Sauvegardez la table d’enregistrement des flux et les fichiers générés nécessaires à un retour en arrière.
2. Notez les identifiants des enregistrements, les titres, les slugs existants, les planifications et les destinations des sorties.
3. Recherchez les appels à `feed:generate` dans les scripts de déploiement, les tâches cron, les planifications manuelles, les tests et le code de l’application.
4. Générez des flux représentatifs et conservez leurs sorties pour les comparer.
5. Pendant le déploiement, suspendez les planifications des flux et laissez se terminer les tâches de flux en cours ou en file d’attente avant de remplacer le paquet et de modifier le schéma.

## Appliquer la mise à jour {/* #apply-update */}

```bash
composer require dragon-code/laravel-feeds:^2.0 --with-all-dependencies
composer check-platform-reqs
```

Comparez le fichier `config/feeds.php` du paquet installé à la copie publiée dans l’application et conservez les paramètres propres à l’application. Ne republiez pas avec `--force` : cela écrase cette copie.

## Ajouter les slugs des flux {/* #feed-slugs */}

La [PR #287](https://github.com/TheDragonCode/laravel-feeds/pull/287) remplace la sélection d’un flux par son identifiant en base de données par une sélection par slug, dérivé avec `Str::slug(title)`.

Si la migration des slugs du paquet n’a pas encore été exécutée, publiez les migrations :

```bash
php artisan vendor:publish --tag=feeds-migrations
```

La commande publie tous les fichiers de migration. Validez les fichiers publiés et supprimez ceux qui sont inutiles.

Définissez l’horodatage du nom de fichier de la nouvelle migration `add_slug_to_feeds_table` après celui de la migration `create_feeds_table` réellement présente dans l’application et avant toute migration d’enregistrement de flux. Cet ordre garantit que `migrate:fresh` ajoute la colonne slug avant que les enregistrements y écrivent. Exécutez ensuite les migrations :

```bash
php artisan migrate
```

La migration ajoute une colonne `slug` qui accepte les valeurs NULL et la remplit à partir des titres existants, y compris ceux des enregistrements supprimés temporairement. Les titres et identifiants existants sont conservés.

:::warning
Si l’application possède déjà sa propre colonne `slug` et que la migration du paquet n’a pas été exécutée, la migration échoue avant de remplir les données. Résolvez ce conflit de schéma avant le déploiement ; ne supprimez pas une colonne propre à l’application sans conserver ses données et mettre à jour le code qui l’utilise.
:::

Examinez les valeurs enregistrées dans `php artisan tinker` :

```php
app(\DragonCode\LaravelFeed\Queries\FeedQuery::class)
    ->all()
    ->get(['id', 'title', 'slug']);
```

Les slugs utilisés pour la sélection doivent être non vides et distincts parmi les enregistrements non supprimés, y compris les inactifs. Des titres différents peuvent produire le même slug après normalisation. Les recherches ambiguës lèvent `MultipleRecordsFoundException` ; les slugs inconnus lèvent `FeedNotFoundException`. Résolvez les collisions ou les slugs vides en modifiant les titres via le modèle de flux.

L’enregistrement d’un modèle de flux recalcule son slug à partir du titre stocké. Les insertions et mises à jour en masse via le constructeur de requêtes contournent ce comportement. Examinez ces écritures et les modèles de flux personnalisés qui redéfinissent les casts ou les événements du modèle.

## Remplacer les identifiants dans les appels de génération {/* #generation-calls */}

Pour l’enregistrement d’identifiant `42` dont le titre stocké est `Products`, le slug après migration est `products`.

Avant :

```bash
php artisan feed:generate 42
```

Après :

```bash
php artisan feed:generate products
```

Dans `2.x`, l’argument est toujours un slug ; une chaîne numérique ne sélectionne plus un identifiant en base de données. L’appel à `php artisan feed:generate` sans argument traite toujours tous les enregistrements actifs. Avec `--target`, remplacez uniquement l’argument d’enregistrement ; les clés des cibles restent identiques :

```bash
php artisan feed:generate products --target=42
```

Mettez à jour les planifications manuelles et les appels de commandes dans le code de la même manière. Avant :

```php
use DragonCode\LaravelFeed\Commands\FeedGenerateCommand;
use Illuminate\Support\Facades\Schedule;

Schedule::command(FeedGenerateCommand::class, [42])->daily();
```

Après :

```php
use DragonCode\LaravelFeed\Commands\FeedGenerateCommand;
use Illuminate\Support\Facades\Schedule;

Schedule::command(FeedGenerateCommand::class, ['products'])->daily();
```

Conservez les paramètres existants des planifications manuelles pour les chevauchements, l’exécution en arrière-plan et la fréquence. Mettez à jour les slugs écrits en dur lorsque vous renommez des enregistrements. `ScheduleFeedHelper::register()` utilise automatiquement les slugs stockés et maintient les verrous de chevauchement liés à l’enregistrement lorsque son titre ou son expression cron change.

`FeedQuery::find(int $id)`, `delete(int $id)` et `restore(int $id)` utilisent toujours des identifiants. Utilisez `FeedQuery::findBySlug(string $slug)` pour sélectionner par slug. Consultez la [génération et la planification](./generation.mdx).

## Vérifier les titres générés {/* #generated-titles */}

La [PR #293](https://github.com/TheDragonCode/laravel-feeds/pull/293) supprime le suffixe `Feed` des titres écrits par `make:feed` dans les nouvelles migrations d’enregistrement ou opérations de déploiement.

Pour `php artisan make:feed ProductsFeed` :

| Valeur | Avant | Après |
| --- | --- | --- |
| Titre d’enregistrement généré | `Products Feed` | `Products` |
| Slug dérivé de ce titre | `products-feed` | `products` |

Les titres existants en base de données et les fichiers d’enregistrement générés auparavant ne sont pas réécrits. Continuez à utiliser le slug réellement stocké pour chaque enregistrement. Le nom de la classe du flux et le nom du fichier de sortie ne sont pas modifiés par ce changement de titre.

## Documentation et développement du paquet {/* #documentation-and-development */}

La [PR #294](https://github.com/TheDragonCode/laravel-feeds/pull/294) renomme la page de documentation Apprentissage automatique en [Agents IA](./ai-agents.mdx). La page est désormais disponible à l’adresse `/ai-agents/` ; les redirections maintiennent les liens vers son ancienne URL.

La [PR #297](https://github.com/TheDragonCode/laravel-feeds/pull/297) définit les nouvelles exigences d’exécution et conserve la documentation de `1.x`. Sélectionnez la version de documentation correspondant au paquet installé ; les résultats de recherche et le contexte des LLM sont limités à cette version.

L’environnement de développement du paquet passe à Pest `^5.0` et Testbench `^11.0`. Ses commandes Pest utilisent `--tia`, avec `--fresh` pour les réexécutions complètes en CI, les benchmarks et les mises à jour des instantanés. Ce sont des dépendances de développement du paquet, pas des exigences pour la suite de tests d’une application.

## Vérifier {/* #verify */}

- Reconstruisez le cache de configuration de l’application s’il est utilisé et redémarrez les workers de file d’attente et les processus persistants du planificateur avec le nouveau code.
- Vérifiez que chaque enregistrement sélectionné possède un slug non vide et distinct, et que les commandes et planifications manuelles l’utilisent.
- Générez un flux pour chaque format utilisé ; vérifiez le nombre et les noms des fichiers fractionnés, ainsi que des sorties représentatives, par rapport aux sorties sauvegardées de `1.x`.
- Vérifiez la sélection des cibles, les planifications automatiques et manuelles et la génération en file d’attente, lorsqu’elles sont utilisées.
- Exécutez les tests de l’application couvrant les modèles de flux personnalisés, les transformateurs, les macros et les sous-classes de préréglage.
- Reprenez les planifications des flux et le traitement des files d’attente une fois les vérifications du schéma et de la génération réussies.

## Revenir en arrière {/* #rollback */}

Suspendez à nouveau la génération des flux et laissez se terminer les tâches en cours. Restaurez le code précédent de l’application, `composer.json`, `composer.lock`, la configuration et les commandes de génération, puis exécutez `composer install` dans un environnement d’exécution compatible.

N’appliquez la politique d’annulation des migrations de l’application qu’après avoir vérifié si le paquet `1.x` restauré utilise déjà des slugs. La méthode `down()` de la migration des slugs supprime uniquement cette colonne ; elle ne restaure ni les titres renommés ni les fichiers générés. Restaurez les données d’enregistrement modifiées et les fichiers de sortie depuis les sauvegardes, si nécessaire. Reconstruisez les caches de configuration et redémarrez les workers et les processus du planificateur avant de reprendre la génération.
